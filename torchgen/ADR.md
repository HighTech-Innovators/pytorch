## Role

`torchgen` is PyTorch's code generation system. It reads operator schemas from `aten/src/ATen/native/native_functions.yaml` (~2,585 operators, 16,230 lines) and generates C++ registration code, Python bindings, selective-build operator lists, structured kernel stubs, and AOTI C shims. It runs at build time, not at runtime.

## Key Files

| File | Purpose |
|---|---|
| `gen.py` | Main code-generator entry point: `run` function; generates `RegisterDispatchKey.cpp`, `Operators.cpp`, `Functions.h`, structured kernel declarations for every backend |
| `model.py` | Data model: `NativeFunction`, `BackendIndex`, `FunctionSchema`, `DispatchKey`, `Argument`, `Return` — parsed from `native_functions.yaml` |
| `context.py` | `with_native_function`, `native_function_manager` decorators that propagate the current `NativeFunction` through generator code |
| `api/cpp.py` | Translates `NativeFunction` to C++ function signatures: argument types, return types, default values |
| `api/dispatcher.py` | Translates to dispatcher call signatures: boxed vs unboxed, argument packing |
| `api/structured.py` | Structured kernel API: generates `meta::` and `structured_*` classes for structured kernels |
| `api/translate.py` | Type translation between `NativeType`, `DispatcherType`, `CppType`, `MetaType` |
| `dest/` | Code generation output targets: `register_dispatch_key.py`, `native_functions.py`, `dispatch_key_function_registrations.py` |
| `selective_build/` | Selective build: `SelectiveBuilder` — reads operator allowlists from model tracing and produces `selected_mobile_ops.h` |
| `gen_functionalization_type.py` | Generates functionalization pass: view-to-copy conversions for composite-functional dispatch |
| `gen_vmap_plumbing.py` | Generates vmap (vectorised map) dispatch plumbing for each operator |
| `gen_aoti_c_shim.py` | Generates C shim functions for AOT Inductor compiled model loading |

## Public Interface

`torchgen` is a build-time tool, not a runtime library. Its public interface is the CLI entry point in `gen.py`:

| Symbol | Description |
|---|---|
| `torchgen.gen.run(source_yaml, output_dir, ...)` | Main generator: reads YAML, calls all registered generators, writes output files |
| `torchgen.model.NativeFunction` | Parsed operator descriptor: schema, dispatch table, structured flag, device guards |
| `torchgen.model.BackendIndex` | Per-backend index of registered kernels: maps `NativeFunction` to `KernelRegistration` |
| `torchgen.selective_build.SelectiveBuilder` | Reads an operator allowlist and determines which operators to include in a selective build |
| `torchgen.api.cpp.argumenttype_type` | Translates an ATen argument type to a C++ type string |

## Dependencies

| Component | Direction | Nature |
|---|---|---|
| `aten/src/ATen/native/native_functions.yaml` | depends-on | Primary input: operator schema definitions |
| [aten/src/ATen](aten/src/ATen/ADR.md) | depended-on-by | ATen's `RegisterDispatchKey.cpp`, `Functions.h`, structured kernel stubs are torchgen outputs |
| [torch/csrc](torch/csrc/ADR.md) | depended-on-by | Python bindings (`python_variable_methods.cpp`) are generated by torchgen |
| PyYAML | depends-on | Parses `native_functions.yaml`; `yaml.safe_load` in `model.py` |

No runtime PyTorch dependencies — torchgen runs with only the Python standard library and PyYAML.

## Runtime Behaviour

`torchgen` runs as a Python script during the CMake build (`cmake --build`). `gen.py:run` loads `native_functions.yaml` via `yaml.safe_load`, parses it into `NativeFunction` objects using `model.py`, groups them by `DispatchKey`, and calls each registered generator (e.g., `dest.register_dispatch_key`, `dest.native_functions`) to produce output files. Selective build mode (`--op_selection_yaml`) additionally runs `SelectiveBuilder` to filter operators and annotate which ones must be included. Generated files are placed in `torch/csrc/autograd/generated/` and `aten/src/ATen/generated/` and compiled as part of the main build.

## Performance Profile

- **Allocation sites**: build-time only; runtime allocation is irrelevant. The generator processes ~2,585 operators in a single Python process; peak memory usage is proportional to the YAML size plus generated file buffers.
- **Synchronization costs**: none — single-process build tool.
- **Data movement**: generated files are written to disk; total output is on the order of several megabytes of C++ source.
- **Redundant or repeated work**: `native_functions.yaml` is parsed once and the resulting `NativeFunction` list is passed to all generators. Incremental builds use CMake dependency tracking to skip regeneration when the YAML is unchanged.

## Design Rationale

Centralising operator schema in `native_functions.yaml` rather than in C++ headers means every consumer (ATen dispatch, Python bindings, selective build, mobile deployment, AOTI) derives its operator set from a single source of truth. This eliminates the risk of divergence between the C++ implementation and the Python API. Code generation rather than runtime reflection is used because the generated registration code is compiled into the shared library, giving zero-overhead dispatch (no hash lookup at runtime for the dispatch table). The `api/translate.py` type-translation layer exists because the same logical operator type (e.g., `Tensor&`) appears differently in different contexts: as a `Tensor&` in native function signatures, as an `at::Tensor*` in boxed dispatch, and as an `int64_t` index in some meta-function signatures.
